# V5.8：不是点个“踩”，而是保存可以复查的问题

这一期把研究成果后的反馈过程做实：用户指出问题，人工核对原文，再把值得检验的问题保存成评测样例。真实模型配置仍未接入，本阶段也没有让系统自动学习或修改答案。

## 反馈时，保存“当时发生了什么”

**Snapshot（快照）**就是一份固定的现场记录。服务器从数据库读取当时的任务目标、策略身份、成果正文、目标结论、证据片段、版本和定位信息，而不是相信网页传来的“原文”。再用 **SHA-256（内容指纹算法）**记录完整性。

因此，资料后来退役或页面重新打开，反馈仍然指向当时的结论。对不存在的成果、别的成果的结论、未结束任务或损坏的数据，接口会明确拒绝。

## 网络中断后重试，只提交一份

**Idempotency（幂等性）**的意思是同一件事重复请求，不重复做。前端为同一个提交意图保留请求标识，数据库通过唯一约束识别它；同一个标识换了内容则报冲突。

实际浏览器测试故意让服务器保存成功后丢掉响应，再点击重试，必须回到原反馈。审阅请求失败时也必须保留已填内容和同一个标识，这轮审查确实发现并修复了表单被自动刷新清空的问题。

## 人工接受，和生成样例必须一起完成

**Transaction（数据库事务）**可以理解为一笔不可拆开的操作。接受反馈、保存审阅意见、生成唯一评测样例，在同一事务内完成；样例写入失败，接受状态也回滚。

审阅还检查 **Version（版本）**：页面拿到的旧版本不能覆盖别人已经完成的审阅。这里的“本地用户”只是操作来源标记，不是假装已经有多用户登录与权限系统。

接受需要人工填写参考答案、验收要求和理由；驳回只保留理由，不生成样例。两者都不会改变原成果、知识库或正在使用的策略。

## 把“平时练习”和“最后验收”分开

**Tuning（调参）样例**用于日常改进；**Holdout（留出测试）样例**留到阶段验收，避免反复针对同一批题调参数。

每条反馈只能生成一种用途的样例。导出时不同用途、真实模型运行、后端演示和录制模型数据不能混在一起。导出后还核对选择的记录与内容指纹，避免下载到错配数据。

这只是用途隔离，不是对拥有本地数据库权限的人隐藏答案。人工参考答案也仍需核对，不因为点击“接受”就自动变成客观真理。

## 页面如何使用

1. 从已完成任务打开研究成果，点击“反馈这条结论”或“反馈这份成果”。
2. 选择漏找资料、理解错误、引用不支持或回答不完整，填写说明并保存。
3. 进入“反馈审阅与样例”，查看保存的原结论、证据和运行模式。
4. 接受时填写参考答案与验收要求，选择样例用途；不认可反馈时填写理由驳回。
5. 选中同用途、同运行模式的已接受样例，确认导出包含的内容，再下载到本机。

导出包含原始问题、成果和证据摘录，可能涉及私人资料，因此不会自动外发。反馈文本用纯文本展示，不执行其中的 HTML、脚本或指令。

## 还没有做到什么？

这期完成的是 **Feedback Review（反馈审阅）与 Evaluation Sample（评测样例）积累**，不是完整的自动改进系统。新样例使用单独标明的格式，没有伪装成固定 60 场景的评测输入，也没有自动生成“模型通过率”。

下一阶段才是：设计新样例的执行与评分接口，在真实模型配置完成后，对相同问题比较旧、新策略的质量、耗时和费用。是否值得继续优化，要由这些实测结果决定。

当前真实验证结果见 [验收记录](acceptance_report.md)。本机 Docker 的兼容处理及明确限制见 [启动修复记录](docker_startup_recovery.md)。
