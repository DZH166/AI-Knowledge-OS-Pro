### R1 · P1：前端依赖落在官方已知漏洞影响范围

- 证据：本次 `npm audit --omit=dev --audit-level=high --json` 返回非零状态，Next.js critical、sharp high。
- 官方公告明确 Next.js 15.5.24 修补 Windows 部署下的远程代码执行问题；另一个公告涉及 AVIF 图片处理。sharp 公告修复版本为 0.35.4。
- 影响要结合部署方式、可达性及图片处理路径判断；这里只确认版本命中，不宣称本机被利用。尤其本项目正在 Windows 开发，不应忽略 Windows 相关公告。
- 修复：在当前主版本内选用已修补版本，同步更新 Next.js 对应检查工具，解除旧 sharp 覆盖锁定并重新生成锁文件，重新执行依赖审计、构建与浏览器验证。不需要为此升级整个应用架构。
- 官方来源：[Next.js Windows 公告](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36)、[Next.js AVIF 公告](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4)、[sharp 公告](https://github.com/lovell/sharp/security/advisories/GHSA-rgj7-g3m4-5g8c)。

### R2 · P1：结论核验会把无关甚至矛盾的结论判成“有证据支持”

- 位置：`backend/app/modules/evidence_agent/claim_verifier.py:35`、`:39`、`:90`、`:100`；产物接入点 `controller.py:2097`。
- 原因：数字范围匹配成功就提前返回，尚未核对主体、单位、否定或关系；其他分支仅有一个词重合也可能通过。“低于”还使用了小于等于判断。多个数字从集合任取一个，也没有绑定它属于什么指标。
- 纯函数反例：原文“旧版日志最多保留 60 天”，结论“系统支持至少 50 名用户”，结果为通过；“接口延迟为 100 毫秒”也能支持“接口延迟低于 100 毫秒”。
- 完整内存 Agent 流程反例：原文 `Alpha latency is 42 milliseconds.`，注入模型结论 `Omega supports at least 40 users.`，任务最终 `completed`，结论 `verification_status=supported`。不是只在一个未使用的辅助函数里出错。
- 影响：引用来源真实、版本定位正确，但结论仍然可能瞎编。当前规则不能充当可靠的 Entailment（原文是否真的能推出结论）证明器。
- 修复：先建立主体—关系—数值—单位绑定和严格比较边界；不能验证的改写返回“未验证”，不要凭词重合标记已支持。保存证据定位与事实支持两个独立状态。随后用人工标注样例评估语义核验，不把换一个大模型直接当作正确性保证。

### R3 · P1：摄取代码仓库时可能越过用户选择的目录边界

- 位置：`backend/app/services/code_repository_service.py:427`、`:430`、`:441`、`:469`；后续向量化在 `:323`。
- 原因：仅检查文件是否为符号链接，没有在目录遍历时排除 Windows junction（目录联接，表现得像文件夹的路径跳转），也没核验解析后的路径是否仍在选定根目录内。
- 实测：在自建临时仓库中放一个指向同一测试区仓库外目录的 junction，扫描结果包含 `linked-outside/fake-config.txt` 及预置哨兵文本。
- 影响：真实摄取可能把仓库外的受支持文本当作代码证据；后续真实 embedding（把文本转换为检索向量）若调用外部服务，可能发送用户没打算纳入的资料。本次仅扫描自建无敏感文本，没有调用外部服务。
- 修复：遍历前拒绝目录联接/重解析点，检查每个目标解析后的包含关系，读取前校验文件类型和大小；补 Windows junction、文件链接、循环路径等测试。不应通过放开整个磁盘读取来处理路径问题。

### R4 · P1：调用次数和输出预算没有贯穿到真正发送请求的地方

- 位置：`backend/app/modules/evidence_agent/controller.py:581`、`:752`；`backend/app/services/providers.py:117`、`:216`、`:230`；`backend/app/services/llm_service.py:99` 附近的结构修复调用。
- 实测：通过假 HTTP 传输返回两次 500 后成功；任务设 `max_model_calls=1`、`max_model_output_tokens=4`，仍产生 3 次传输尝试，落库输出 20 tokens，请求体不含输出上限。实际外部网络调用为 0。
- 原因：上层调用前只预占一次逻辑调用，底层独立重试；输出、费用和耗时主要在响应后记账。响应后拒收结果，可以保护产物，但无法追回已经发送的请求或费用。
- 修复：每次 HTTP 尝试和结构修复都消费同一个预算；传入剩余输出 token 上限和剩余时间，调用前估算上下文，未知价格时不要宣称硬费用上限。tokens 指模型处理文本时计量的小片段。

### R5 · P2：页面允许的长问题会在 Agent 中途触发校验异常

- 位置：`frontend/modules/evidence-agent/contract.ts:177`、`backend/app/schemas/agent_schema.py:44` 允许 12,000 字符；`backend/app/services/agent_model.py:48`、`:113` 仅允许 4,000；`controller.py:1771` 和 `:1993` 直接传原目标。
- 实测：4,014 字符目标通过入口校验并开始运行，在 assess（判断证据够不够）阶段抛 `ValidationError: max_length 4000`；当时数据库仍是 `running / assess`。未宣称已实测最终队列重试耗尽的结果。
- 修复：统一产品入口和内部限制；若要支持长任务，明确做有边界的目标压缩并保留原文；不能让用户开始以后才遇到未转换的异常。

### R6 · P2：工作台失败重试可能创建重复任务

- 位置：`frontend/components/evidence-agent/Workbench.tsx:95`、`:107`；`frontend/modules/evidence-agent/http-sse-adapter.ts:49`；`frontend/components/evidence-agent/runtime.ts:53`。
- 触发路径：POST 已成功创建任务，但随后读取任务详情失败；适配器把整个启动当作失败，工作台重试重新生成 request_id，后端无法识别还是原来那次意图。
- 证据：代码路径确认；内存后端实测相同请求标识会返回同一任务，换标识则创建第二个任务。本次未执行浏览器断网复现，不冒充整页端到端实测。
- 修复：同一份提交保留一个请求标识；拿到创建回执立即保存任务 ID，后续读取失败只重读该任务。Idempotency（幂等）就是同一次操作重复发送，不会重复做事。

## 不冒充缺陷的能力边界

1. **中文关键词检索仍偏简单。** canonical sparse 路径主要按空格拆分和子串匹配。原文“系统支持离线缓存。”，查询“离线缓存”命中 1 条，“系统支持离线缓存吗”命中 0 条。此为关键词分支实测，不代表已配置的向量检索也必然失败。可用中文分词、词项索引和问题改写改进，先用真实中文问题测收益。
2. **当前评测还不能证明 Agent 比同等检索能力的普通 RAG 更好。** 新报告中同一固定集的 retrieval_only 多跳成功率与 Agent 都是 100%；README 的提升对比对象是较弱的单次 sparse top-4 代理，已注明不是历史系统原样重跑。下一步应控制检索器、语料、模型和预算一致，再比较是否值得多走几步。
3. **反馈是可审阅样例，不是自动学习。** 接受反馈并导出，并不会让模型自动变聪明，也不会自动改变策略。需要样例执行器和可核对的评分流程。
4. **默认仍是可信单用户本地应用。** 不把缺少多租户系统算本期缺陷，但不能拿现状直接开放公网。Docker compose 当前端口未限定 127.0.0.1；对外部署前需要重新核对服务监听、鉴权、上传限额、敏感内容和权限边界。
5. **交付环境还不够统一。** 本地 compose 使用 Qdrant 1.12.5，严格 E2E 默认使用 1.18.0；Python 依赖大多只有下限；本机语言版本与 CI 不同。应建立一份能在干净机器复现的验证基线。
6. **文档仍有旧标记。** SECURITY.md 写支持 V3.6，CI 发布产物名仍有 V5.2；这些比核心缺陷优先级低，但正式交付要统一。

### 暂缓的方向

暂不增加多智能体协作、知识图谱、模型微调、分布式微服务或新的复杂优化算法。除非真实使用记录证明它们能解决明确问题，否则会增加学习与维护成本，未必增加项目说服力。
