# V5.7.1：这轮到底升级了什么，怎么实现的？

这轮是可靠性修订，不是再堆一批新功能。项目已有“找资料—执行研究任务—检查证据—生成成果—比较检索策略”的主线；本次重点是让这条主线在重复点击、网络中断、后台重启、历史数据升级等情况下仍然可信。

## 1. Agent 和 RAG 分别负责什么？

**RAG（Retrieval-Augmented Generation，检索增强生成）**：回答前先从你的资料中找相关内容，再让模型据此作答。它解决“回答依据从哪里来”。

**Agent（智能体）**：围绕一个任务，决定下一步是规划、检索、检查证据、继续查找、请求澄清，还是生成成果。它解决“任务接下来怎么做”。本项目用持久化状态和明确的执行步骤控制这个过程，而不是给模型一段很长的提示词后完全放任执行。

**Evidence（证据）**：回答引用的原文片段。项目记录资料版本、内容指纹和定位信息，因此引用能返回当时的文档页码、媒体时间或代码行。**Artifact（成果）**是任务最终留下的可检查内容，**Claim（结论）**则是其中需要证据支持的具体说法。

上述是已有主线。本轮主要加固下面这些运行与评测环节，没有重新实现一套 Agent。

## 2. 后台重启后，也不能突破预算

**原来的风险**：任务创建时检查了预算，但恢复后再次领取任务时可能绕过限制。

**现在如何实现**：领取和恢复任务共同检查累计评测次数、截止时间和实验状态；不满足条件就不能调用评测器。时间先统一为 **UTC（协调世界时）**，避免北京时间和数据库中的无时区时间直接混比。

**Study（实验研究）**是一组策略试验；**Trial（单次试验）**是其中一个候选策略的评测。预算限制针对整组实验累计执行，不是每次恢复就重新获得额度。

## 3. 多个后台进程同时操作，也只认一份结果

**原来的风险**：两个请求都看到“还没开始”，可能各自开始一轮；已经超时的旧进程也可能覆盖新的执行结果。

**现在如何实现**：

- 用数据库写锁把同一 Study 的关键操作排队处理。
- 给每次执行分配唯一标识；保存结果时核对当前执行身份。
- 把结果、评分和推荐放入同一个 **Transaction（数据库事务）**，即全部成功才保存，任何一步失败就整体撤回。
- 把“生成策略草稿”和“记录转换成功”也放入同一事务；两个并发请求只能拿到同一个草稿。

**Lease（租约）**可以理解为“这一小段时间由谁执行任务的凭证”。唯一执行标识用于阻止已经失效的旧执行者继续写入。

## 4. 调参数要看证据，不能只信一个漂亮总分

**Optimizer（优化器）**会提出候选检索参数，运行固定评测，再比较它们与基准策略的差异。它不是训练基础大模型，也不会自动把候选策略发布为正式策略。

**现在如何实现**：评测报告必须同时满足完整的 **Hard Gates（硬性通过条件）**，并核对报告、数据集、评测器和策略的 **SHA-256（内容指纹算法）**。报告声称“全部通过”，但逐题结果或引用指标与之矛盾时，会被拒绝用于推荐。

推荐按实际分数排序，再用稳定序号处理同分。**Pareto Frontier（帕累托前沿）**保留的是在质量、延迟等多项目标上不能被另一个方案全面超过的候选，不等于存在一个对所有人都最好的方案。

三个 Trial 的对比报告现在覆盖全部三组两两比较。对于旧版只存了分类汇总的数据，系统从保存下来的真实逐题报告恢复；报告缺失或无法验证时明确报错，不虚构题目结果。

## 5. “参考上一次实验”，不等于让历史悄悄变化

**Warm Start（暖启动）**：开始新实验时参考旧实验的观察结果，减少完全从头尝试。

**现在如何实现**：子实验创建时保存父实验观察的快照。父实验后来继续运行，不会改变已经创建的子实验起点。数据库通过 **Alembic（数据库结构迁移工具）**增加快照字段，并验证升级、降级和再次升级。

老实验没有保存过的创建时快照无法倒推。迁移只能保存当时仍存在的父数据，并明确标记它是在迁移时取得的。

一个重要术语更正：当前候选生成采用线性趋势和随机探索，准确名称是“观察引导搜索”。它没有实现贝叶斯后验或不确定性估计，因此不把它包装成真正的“贝叶斯优化”。历史模块文件名保留，不代表算法能力已经实现。

## 6. 页面不需要靠反复刷新才能知道结果

**现在如何实现**：页面定期读取后台进度，但用请求顺序标识和取消机制丢弃过时响应。更新时保留当前页面和选择状态，不反复卸载页面。后台返回哪些操作可用，页面据此显示按钮，避免前后端各自猜一套规则。

**Idempotency（幂等性）**：同一件事重试多次，最终只做一次。页面为同一个创建意图保留请求标识；即使后端已创建成功、网络却没把响应送回来，重试仍回到原来的实验，而不是再创建一个。

事件记录现在会按游标继续翻页，不再只显示最前面的一批；超出明确上限或分页异常时显示错误，不悄悄截断。

## 7. 分享链接刷新后仍可撤销

**Run Trace（任务执行轨迹）**：任务经历了哪些步骤及其结果。

**现在如何实现**：分享列表从服务器读取，不只存在页面内存里。因此刷新后仍知道哪些链接有效，也能撤销指定链接。列表加载完成前禁止创建，防止较晚返回的旧列表覆盖刚创建的链接。过期或撤销后的访问返回不存在；分享接口禁止缓存，避免缓存继续展示已失效的内容。

这是受控的只读分享，不代表已实现完整的多用户权限体系。

## 8. 怎么证明这些不是“代码看起来不错”？

- **Unit Test（单元测试）**：验证一个模块的输入、输出和异常情况。
- **Integration Test（集成测试）**：验证数据库、模块及迁移能否共同工作；并发问题需要真的发出并发请求，不能只重复顺序调用。
- **E2E / End-to-End Test（端到端测试）**：从浏览器操作开始，经过后端和后台队列，再检查页面上的最终结果。
- **Strict（严格模式）**：缺少浏览器、Docker 或后台服务就失败，不能把“没执行”算作通过。
- **Release Archive（发布压缩包）**：验证文件清单、内容指纹及与当前代码是否一致，并排除密钥、数据库和上传文件。

本轮测试数字与命令见 [验收报告](acceptance_report.md)。真实 Redis（队列数据服务）、RQ（Python 后台任务执行库）和 Qdrant（向量检索数据库）参与联动测试；模型输出使用明确标注的测试数据。生产构建单独检查，浏览器联动测试使用开发服务器。这些证据验证软件流程，不证明真实模型一定答得好。

## 下一阶段怎样收尾？

优先形成一个面试可完整演示的场景：导入一份资料，提出一个跨段落问题，展示检索与引用，比较两种策略，解释失败案例，再导出结果。

随后再做真实模型接入和一小组未参与调参的验证题，记录质量、耗时和实际调用成本。进一步的登录权限、多人隔离、服务端数据库并发和部署运维，应根据是否真的要开放给其他用户来决定，不用为了简历无限叠功能。
