# 溯知项目技术点与亮点：通俗解释版

这份说明保留专业词，但每个词都紧跟中文解释。重点不是“堆了多少框架”，而是每次升级解决了什么问题，以及代码是怎么做到的。

## 1. 最早的 RAG：先让系统能从资料里找答案

**RAG（Retrieval-Augmented Generation，检索增强生成）**的基本思路是：用户提问后，系统先从资料库检索相关片段，再把片段交给模型生成回答。

实现方式：文件解析成文本，切成 Chunk（文本片段），生成 Embedding（数字向量），写入 Qdrant（向量数据库），回答再附带 Citation（引用）。这一阶段证明了基础 AI 应用能力，但资料更新后旧引用可能说不清版本。

## 2. EvidenceIndex：先把“证据身份”修清楚

项目用 `Source → Revision → IndexRevision → Chunk → Hash → Locator` 给每条证据建立完整身份证。新资料先 Stage（暂存），向量和 Manifest（清单）写成功后才 Activate（激活）；旧版本 Retire（退休）但不抹掉。历史成果继续固定原来的版本、片段、指纹、页码、时间戳或代码行。

亮点：解决普通 RAG 很少认真处理的引用漂移、旧版本污染和证据不可回放。

## 3. 从 RAG 变成 Agent：让系统能分步骤完成研究

**Agent（智能体）**不是多调用几次模型，而是围绕目标持续执行并保存状态。流程包括 Route（路由）、Plan（计划）、Retrieve（检索）、Assess（证据判断）、Synthesis（综合）、Verify（校验）和 Artifact（研究成果）。每个复杂目标会拆成 Requirement（子问题），每条事实 Claim（结论）绑定真实证据。

证据不足时系统生成 Evidence Gap Report（证据缺口报告），告诉用户缺什么，而不是硬编答案。

## 4. Durable Runtime：浏览器关了，任务也不能丢

**Durable Runtime（可持久恢复的运行系统）**把 Run、Plan、ToolCall、ModelCall、Event、Checkpoint 全部写入 SQLite。Redis/RQ 负责后台任务；Outbox（事务发件箱）保证数据库更新和发送任务不会只成功一半；Lease（租约）与 CAS（比较并更新）防止两个 Worker 同时写；Execution Fence（执行栅栏）阻止取消后的迟到结果；Dead Letter（死信）隔离反复失败的任务。

这部分体现后端一致性、并发控制和崩溃恢复，不是聊天页面包装。

## 5. Human-in-the-loop：模型没有最终权限

**Human-in-the-loop（人工参与决策）**让用户批准、拒绝、修改标题、补充信息、暂停、恢复或取消。每条命令带运行版本和 Proposal Digest（提案内容指纹）。内容变了，旧批准自动失效。模型只能提出建议，权限、预算和写入由确定性代码控制。

## 6. Claim-level Evidence：不是文末随便放几个链接

**Claim-level Evidence（结论级证据）**让每条事实至少关联一个 EvidenceRef。文档跳到 PDF 页，媒体跳到时间戳，代码跳到文件和行号，历史退休版本也能打开。Entailment Gate（事实蕴含门禁）还会拒绝数字、否定、范围和实体不一致。

## 7. V5.1 真实运行验证：不用模拟冒充生产

系统在真实 Redis、RQ Worker 和 Qdrant 环境连续测试。每次分配独立端口、数据库、队列、集合、Worker 和容器名，成功或失败都只清理本次资源。真实验证还发现 RQ 不接受冒号任务编号，并据此修复；这个问题内存模拟器发现不了。

## 8. V5.2 Run Trace：给 Agent 装上可解释黑匣子

**Run Trace（运行轨迹）**展示运行编号、Trace ID、事件顺序、耗时、工具版本、模型调用摘要、策略、预算、失败归因和 Replay Digest（重放指纹）。后端只读持久化事实，不重新调用模型或工具。公共事件只允许白名单字段，私有事件只返回“已脱敏”，工具参数、模型 prompt 和检查点状态都不返回。

这叫 **Projection Replay（投影重放）**：重建发生过什么，但绝不重放历史外部副作用。

## 9. V5.2 Evaluation Studio：每次升级先证明没有退步

**Evaluation Studio（智能体评测中心）**把命令行 60 场景评测做成持久化功能：点击启动后，后端同事务写入 Evaluation 和 Outbox；Worker 在独立临时目录运行固定脚本和固定数据集；子进程清除模型密钥；报告必须通过结构、哈希、案例、类别、指标、门禁和外部调用检查，才写成历史快照。

页面可以看指标、门禁、场景、全部案例和失败原因，也能按状态筛选或重新运行。

## 10. Snapshot Comparison：不允许拿不同试卷硬比较

**Snapshot Comparison（快照对比）**先检查 Schema Version、Dataset Hash、关键指标和门禁集合。条件不同就显示 Incomparable（不可比较）；条件一致才计算 Improved（提升）、Stable（稳定）或 Regressed（回退），同时列出新增失败和已修复案例。

现在还会显示两边的 Policy Fingerprint（策略指纹）。它变化了不等于变好或变坏，只表示两次评测使用的决策规则不同，页面会明确提醒这是一次策略变化对比。

## 11. Failure Triage：失败不能只显示“出错了”

**Failure Triage（失败归因）**把故障分成队列失败、Worker 中断、超时、坏报告、门禁失败、预算耗尽、证据不足、工具失败、Provider 不可用、取消和未知。分类只读确定性事实，不让模型猜；每类给出依据、是否可重试和下一步建议。

## 12. 对抗性审查：专门用“坏情况”攻击自己的实现

**Adversarial Review（对抗性审查）**不是只看正常流程，而是故意塞入密钥形状、私有事件、坏报告、重复请求、超时任务、迟到结果、不同数据集和高 CPU 压力。

这次具体修了四类隐蔽问题：Run 目标和私有策略可能泄密，因此所有可见文本先经过 Sanitization（脱敏检查）；评测子进程可能继承 AWS、Google 等未知凭据，因此环境变量改为 Allowlist（白名单），没列出的全部不给；租约测试原来依赖固定睡眠，因此改为直接观察数据库续租；指标名称散落多处，因此建立 Metric Catalog（指标目录）作为 Single Source of Truth（单一事实来源）。

最终后端 536 项通过、1 项跳过；前端 98 项通过；两套独立的 Redis、RQ、Qdrant、后端、前端和浏览器完整流程各 36 项全部通过，并清理了本轮所有资源。评测入口还会拒绝 NaN（非数字）和正负 Infinity（无穷值），避免异常数字伪装成有效分数。

## 13. 对 AI 应用开发岗位的核心价值

> 我做的不是调用大模型的聊天壳，而是一套以不可变证据为核心、能分步研究、可人工审批、可崩溃恢复、可解释追踪、可固定评测和自动防回退的 Agent 应用系统。

项目同时体现 RAG、多模态处理、Agent 状态机、证据版本、引用追溯、事实校验、Redis/RQ 后台任务、事务一致性、并发隔离、前后端数据契约、自动评测、质量门禁、浏览器 E2E 和隐私脱敏。

## 14. 当前诚实边界

- 没有配置真实大模型，因此不宣称真实回答质量。
- 固定 60 场景主要验证架构、安全、持久化和回归。
- 当前面向单用户本地工作区，不是多租户 SaaS。
- SQLite 适合个人项目和演示；更大规模可以再迁移 PostgreSQL。
- 事件重放不会重新执行历史外部操作，这是安全设计。
