# 这一步做了什么，为什么这样改

这一阶段只做两件事：先修后台进度连接的报错，再让中文问题更容易找到正确原文。阶段编号是 V5.12，产品版本仍为 V5.8，不代表又接入了新的大模型。

## 1. 先检查任务存在，再开始发送进度

以前就像服务员先说“开始上菜”，才发现订单根本不存在：后台已经告诉页面连接成功，后面再抛出“任务不存在”，就无法正常改成错误响应。

现在在开启 SSE（服务器持续向页面发送进度事件的连接）之前，调用已有任务查询。找不到任务就直接返回 404（资源不存在），并带上 Request ID（请求编号，方便在日志中定位同一次请求）。正常任务的事件格式、断线后从 Cursor（已读事件位置）继续读取都不变；没有为了检查而等待第一条事件。

这修的是“连接开始时任务已经不存在”的错误路径，不表示数据库故障或连接中断以后永远不会报错。

## 2. 不要求你把中文问题手动加空格

例如资料写“混合检索结合向量与关键词，减少术语漏召回”，你问“为什么混合检索能减少漏召回？”，以前可能把整句当成一个词，找不到。

现在先做 Normalization（把全角字符、大小写等写法统一），再从中文里提取相邻的两字和三字片段，例如“混合”“检索”“漏召回”。即使提问顺序与原文不同，也能凭共同文字找到候选。英文标识符和数字保留整体，不随意切成字母。

这叫 Lexical Retrieval（按字面词项查找），不是让系统突然学会所有同义词，也不是完整中文分词。完全没有共同文字的表达，仍需要后续真实向量检索等能力单独验证。

## 3. 重复关键词不能轻易挤掉真正有用的资料

一段文字把“检索、超时”重复五十遍，不应该排在“检索请求超时后执行重试”的规则前面。

现在同一词项出现多少次，都只按“有没有命中”计算一次，优先看问题里的有效文字覆盖了多少；稍长的片段有封顶权重，文本浓度只作有限修正。EvidenceIndex（维护原文版本与引用身份的证据索引）和 HybridRetriever（把向量与关键词候选合在一起的混合检索器）共享这套规则，避免一个排好了、另一个又按重复次数排回去。

原有 RRF（按候选排名合并两路检索的方法）、可选 Reranker（再次判断候选相关性的重排器）以及最终分数过滤没有改。这次没有接入或验证真实重排模型。

## 4. 先限定资料范围，再选择最相关的结果

发现的另一个问题是：你指定了某个历史版本和来源，但其他来源可能先占满前一百个候选，正确来源反而被截掉。

现在先求出“用户允许的空间、来源、版本”的交集，再检索排序。引用仍绑定原来的 Revision（资料版本）、Chunk（原文片段）、Hash（内容校验指纹）和 Locator（页码等定位），不会为了找到更多结果就混进旧版或别的知识库。

## 5. 用同一张考卷检查改前与改后

人工先写好 24 个问题与答案标签，再运行旧算法，最后运行新算法；题目、标签和评测程序的摘要都保持一致。20 个有答案的问题，两条路径的首条命中率从 45% 和 60% 提高到 100%；4 个无答案反例没有误召回。这是小型合成样本，不是“整个项目准确率 100%”。

Hit@1 / Hit@5（正确原文是否排在第一条／前五条）检查有没有找到；MRR（第一个正确答案排名倒数的平均值）也反映排得靠不靠前。负例、空间隔离和引用身份单独检查，不拿它们凑高正例准确率。

CI（每次推送代码后自动执行的云端检查）现在也会运行这套题并保留报告；测试另外验证评测器不会隐瞒漏召回。原来的后端、页面、数据库迁移和完整流程检查继续保留，不只跑新增测试。

## 后面优先做什么

先用一批获准使用的真实中文资料和人工问题验证效果，再扩大困难负例，例如文字很像但条件、年份、版本不同的资料；这比继续加复杂名词更有价值。之后再按实测瓶颈处理大资料库加载、检索速度和服务健康提示。真实大模型效果仍需单独接入、单独验收。
